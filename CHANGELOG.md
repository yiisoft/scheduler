# Yii Scheduler Change Log

## 1.0.0 under development

- Chg #53: Analyse the code with [PHPStan](https://phpstan.org/) instead of Psalm, and run mutation testing with Infection itself rather than the Roave plugin that brought Psalm with it. `CronExpressionTrigger::getNextRunDate()` and `getNextRunDateAtOrAfter()` now say they answer with a date rather than with a date or null, which is what they have always done (@KalimeroMK)
- New #34: Let each task say what becomes of the runs it missed instead of the schedule saying it for all of them: `MissedRuns::All` replays them oldest first up to a limit, `MissedRuns::Last` runs only the newest due, and `MissedRuns::Skip` runs none of them and leaves the task to resume at its next run. `RecurringTask::withMissedRuns()` answers for one task and `Schedule::missedRuns()` for every task that has not; `processOnlyLastMissedRun()` is the older name of `missedRuns(MissedRuns::Last)`. The answer is not part of a task's identifier, so changing it leaves the runs already recorded where they are (@KalimeroMK)
- New #34: Let each task say what becomes of the runs it missed instead of the schedule saying it for all of them: `MissedRuns::All` replays them oldest first up to a limit, `MissedRuns::Last` runs only the newest due, and `MissedRuns::Skip` runs none of them and leaves the task to resume at its next run. `RecurringTask::withMissedRuns()` answers for one task and `Schedule::missedRuns()` for every task that has not; `processOnlyLastMissedRun()` is the older name of `missedRuns(MissedRuns::Last)`. The answer covers runs nobody has taken yet, so a claimed run handed back after its reclaim window is delivered whatever the answer was, and it is not part of a task's identifier, so changing it leaves the runs already recorded where they are (@KalimeroMK)
- New #34: Let each task say what becomes of the runs it missed instead of the schedule saying it for all of them: `MissedRuns::All` replays them oldest first up to a limit on how many of them one tick replays, which the run due now is never held back by, `MissedRuns::Last` runs only the newest due, and `MissedRuns::Skip` runs none of them and leaves the task to resume at its next run. `RecurringTask::withMissedRuns()` answers for one task and `Schedule::missedRuns()` for every task that has not; `processOnlyLastMissedRun()` is the older name of `missedRuns(MissedRuns::Last)`. The answer covers runs nobody has taken yet, so a claimed run handed back after its reclaim window is delivered whatever the answer was, and it is not part of a task's identifier, so changing it leaves the runs already recorded where they are (@KalimeroMK)
- Bug #36: Fix a scheduler that outlives its ticks never picking up the rest of a backlog its bound left behind; only a write by another process moved the revision the pending runs are held against, so the same process kept an empty heap over work nobody else was going to touch and the replay waited for a restart (@KalimeroMK)
- Enh #36: Bound how far one tick walks the backlog of a single task to ten thousand occurrences, a week of a task due every minute, and leave the rest to the tick after it; a trigger without `TriggerRangeInterface` can only be walked a date at a time, so a task whose last run was a year ago used to spend a year of dates before emitting the first one. Nothing is skipped: each tick seeds from the checkpoint and carries on where the one before stopped (@KalimeroMK)
- New #36: Answer a bounded part of a cron sequence as well: `CronExpressionTrigger` implements `TriggerRangeInterface`, walking the expression itself, so a batch costs its own length rather than the span it is taken from. An expression names a minute, so a date already past the start of one is answered with the run after it rather than the one just missed (@KalimeroMK)
- New #36: Add `TriggerRangeInterface`, so a trigger can be asked for a bounded part of its sequence instead of one run date at a time: `getNextRunDateAtOrAfter()` answers with the run at the date asked about, and `getRunDates()` with the runs between two dates, at most as many as asked for. `PeriodicTrigger` implements it by counting intervals from its anchor, so a batch costs its own length and one search. The dates are the ones the trigger gives one at a time, in the same order (@KalimeroMK)
- Bug #30: Fix two tasks differing only in the timezone their cron expression is read in, in the date their interval is counted from or stops at, or in the payload of the queue message they push, sharing one generated identifier, so that a schedule rejected the second as a duplicate and a checkpoint held the runs of both under one record; a trigger now describes itself with its timezone and its bounds, a message task is told apart by its payload as well as its type, and a cron task takes its identifier from that description rather than from the expression alone (@KalimeroMK)
- Bug #30: Fix two tasks differing only in the timezone their cron expression is read in, in the date their interval is counted from or stops at, or in the payload of the queue message they push, sharing one generated identifier, so that a schedule rejected the second as a duplicate and a checkpoint held the runs of both under one record; a trigger now describes itself with its timezone and its bounds, a message task is told apart by its payload as well as its type, and a cron task given a timezone takes its identifier from that description rather than from the expression alone (@KalimeroMK)
- New #45: Report what the scheduler is doing to the terminal as OSC 7501 program status, so that `schedule:run` shows the due batch and its outcome and a `schedule:work` daemon waiting for its next run can be told from a dead one; `--no-program-status` turns it off, and nothing is written to a redirected output, in quiet mode or with `--no-ansi` (@KalimeroMK)
- Enh #25: Make the core usable without a framework: `Schedule::lock()` takes a `LockInterface` of this package rather than a yiisoft/mutex one, with `MutexLock` adapting a mutex for it; `symfony/console` moves out of the package's dependencies and into its suggestions, and the handling of a console command task moves out of `CallableTaskHandler` into a `ConsoleTaskHandler` in front of it. A handler now passes on what it does not recognise, so the bundled configuration builds a chain from whatever is installed, and a schedule of callables runs with neither a console application nor a queue producer. Removed the unused `ScheduleProviderInterface` (@KalimeroMK)
- Initial release.
